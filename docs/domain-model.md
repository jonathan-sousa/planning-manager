# Modèle de domaine

Tables Aurora DSQL définies dans `api/db/schema.ts` (Drizzle). L'API n'est accessible qu'au groupe `MANAGERS`. Il n'y a pas d'autorisation par propriétaire : les données du service sont partagées entre ses managers.

> En base : `Grade` à `RuleSettings` (référentiels), `Planning` et `Assignment`. `AgentBalance` et `SolveRun` décrivent le modèle cible (voir la feuille de route dans [architecture.md](architecture.md)). Les noms ci-dessous sont ceux des entités ; les tables sont en `snake_case` pluriel (`skillIds[]` est la table `agent_skills`).

## Conventions

- **Dates et heures** : dates en `YYYY-MM-DD`, heures en `HH:mm`, durées en minutes calculées en heure de Paris (les nuits de changement d'heure font 11h ou 13h). Tout calcul de calendrier, de jour férié ou de durée passe par `api/calendar.ts`, seul endroit qui manipule un `Date`.
- **Minimisation RGPD** : aucun code révélant un motif médical (`ABS` générique, pas `MAL`).
- **Identifiants** : UUID aléatoires (`gen_random_uuid()`), jamais de séquence monotone (répartition des écritures DSQL). Exceptions : table de liaison `agent_skills` (clé composite) et ligne unique `rule_settings` (`default`). Les identifiants composites du tableau (`[agentId, date]`) deviennent des contraintes d'unicité.
- **Écritures du solveur** : via SQL dans une transaction unique (≤ 3 000 lignes), avec vérification de `plannings.version` dans la même transaction.
