# Modèle de domaine

Tables Aurora DSQL définies dans `api/db/schema.ts` (Drizzle). L'API n'est accessible qu'au groupe `MANAGERS`. Il n'y a pas d'autorisation par propriétaire : les données du service sont partagées entre ses managers.

> En base : `Grade` à `RuleSettings` (référentiels). `Planning`, `Assignment`, `AgentBalance` et `SolveRun` décrivent le modèle cible (voir la feuille de route dans [architecture.md](architecture.md)). Les noms ci-dessous sont ceux des entités ; les tables sont en `snake_case` pluriel (`skillIds[]` est la table `agent_skills`).

| Modèle             | Champs clés                                                                                                                                                                                                                                     | Notes                                                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Grade`            | `code` (IDE, AS, ASH…), `label`, `sortOrder`                                                                                                                                                                                                    | Configurable, pas un enum figé.                                                                                                                  |
| `Skill`            | `code` (IOA, SAUV…), `label`                                                                                                                                                                                                                    | Fonctions ou compétences optionnelles.                                                                                                           |
| `Agent`            | `firstName`, `lastName`, `gradeId`, `skillIds[]`, `workTimeRatio`, `nightMode` (`DAY_ONLY` / `NIGHT_ONLY` / `MIXED`), `hoursRegime` (`STANDARD_1607` / `VARIABLE_REST_1582` / `NIGHT_1476` / `MIXED_PRORATA`), `active`, `startDate`, `endDate` | `nightMode` dit ce que le solveur peut affecter ; `hoursRegime` fixe l'obligation horaire.                                                       |
| `ShiftType`        | `code` (J, N, CA, RTT, RH, ABS…), `label`, `kind` (`WORK` / `ABSENCE` / `REST`), `startTime`, `endTime`, `breakMinutes`, `countedMinutes`, `isNight`, `color`, `archived`                                                                       | Absences et repos sont des « postes » de la grille. Un poste déjà utilisé ne se modifie jamais en place : on l'archive et on en crée un nouveau. |
| `CoverageNeed`     | `shiftTypeId`, `gradeId`, `skillId?`, `dayKind` (`WEEKDAY` / `SATURDAY` / `SUNDAY_HOLIDAY`), `minCount`, `targetCount?`                                                                                                                         | Grille de besoins standard.                                                                                                                      |
| `CoverageOverride` | `date`, `shiftTypeId`, `gradeId`, `skillId?`, `minCount`                                                                                                                                                                                        | Exceptions datées.                                                                                                                               |
| `AgentRequest`     | `agentId`, `startDate`, `endDate`, `kind` (`ABSENCE_APPROVED` / `WISH_OFF` / `WISH_SHIFT`), `shiftTypeId?`, `comment`                                                                                                                           | Absence validée = cellule verrouillée ; souhait = contrainte souple.                                                                             |
| `Planning`         | `month` (identifiant `YYYY-MM`), `status` (`DRAFT` / `VALIDATED` / `PUBLISHED`), `version`, `publishedAt`, `notes`                                                                                                                              | `version` protège l'application du solveur contre les éditions concurrentes.                                                                     |
| `Assignment`       | identifiant `[agentId, date]`, `month` (index secondaire), `shiftTypeId`, `countedMinutes`, `locked`, `source` (`MANUAL` / `SOLVER` / `REQUEST`), `acceptedViolations[]`, `comment`, `updatedBy`                                                | Une cellule de la grille. ## Conventions

- **Dates et heures** : dates en `YYYY-MM-DD`, heures en `HH:mm`, durées en minutes calculées en heure de Paris (les nuits de changement d'heure font 11h ou 13h). Jamais d'aller-retour par un `Date` UTC.
- **Minimisation RGPD** : aucun code révélant un motif médical (`ABS` générique, pas `MAL`).
- **Identifiants** : UUID aléatoires (`gen_random_uuid()`), jamais de séquence monotone (répartition des écritures DSQL). Les identifiants composites du tableau (`[agentId, date]`) deviennent des contraintes d'unicité.
- **Écritures du solveur** : via SQL dans une transaction unique (≤ 3 000 lignes), avec vérification de `plannings.version` dans la même transaction.
